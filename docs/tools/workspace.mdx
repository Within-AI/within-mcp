| Tool | When to use |
|---|---|
| `list_accessible_workspaces` | List the customer's workspaces and which one is currently active. |
| `list_users` | List active human users in the current workspace, subject to directory permissions. |

These workspace tools are read-only. Use `list_accessible_workspaces` to orient at the start of a session or to confirm which workspace the assistant is reading from before drilling in.

## User directory

`list_users` lists active human users in the current workspace. It requires `user.view_list` and returns names, email addresses, resource keys, and workspace roles. Workspace admins also receive `last_login_at`, the last successful WorkOS sign-in time; null means no sign-in has been recorded. This field is omitted for other callers.

Inputs: `limit` defaults to 25 (1–100); `offset` defaults to 0 (minimum 0). The response contains `items`, `total`, `limit`, and `offset`. Like every tool, it also accepts the shared `context` and `mcp_thread_id` arguments.

Use returned user resource keys to filter contributors in `list_sessions`.

## Switching workspaces

Each session is scoped to a single workspace. To switch, how you do it depends on how you authenticated:

- **OAuth** — disconnect the Within connection in your client and reconnect. The reconnect flow shows a workspace picker.
- **API key** — keys are bound to the workspace they were generated in. Generate a new key in the other workspace and swap the Bearer token in your client.

See [Authentication → Switching workspaces](/authentication#switching-workspaces) for the full walkthrough.

## Common chains

- **Confirm workspace at start**: `list_accessible_workspaces` to see which workspace is active before drilling in
