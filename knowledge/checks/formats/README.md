# A3 formats v0.1

The two data formats Future State Design reads and writes for a set of processes, and fictional examples of each.

| File | What it is |
|---|---|
| `set-map-v0.1.schema.json` | The set map: work objects, their states, typed links between processes, actors, context neighbours, open points, and the freeze pins (`snapshot_cutoff`, `process_versions`). v0 set maps stay valid. |
| `current-state-graph-v0.1.schema.json` | The workflow bundle (schema_version 2) with the A3 lane fields. One schema carries both the current state (`variant: current-state`) and the future state (`variant: future-state`). |
| `examples/set-map.example.json` | A fictional set map. |
| `examples/current-state.example.json` | A fictional current state drawn from that set map. |
| `examples/future-state.example.json` | A fictional future state of the same set. |

The repository's A3 formats schema test validates every example against its schema with `jsonschema` (draft 2020-12, with format checks) and checks the cases below.

The finals already carry the extension id change: `extensions` accepts `a3-lanes-v0.1`, and still accepts `a3-lanes-v0` on read. New bundles write `a3-lanes-v0.1`. The `$id` values (`within-adk/...`) are kept as they are. The test pins both hashes, so any later edit has to be listed here with its reason.

## The examples

A fictional letting agent, Northwind Lettings, handles repair requests. Its systems (Fixit maintenance system, Northwind tenant portal, Callbox phone system, Pingly text messaging), people and repair firm are invented. The examples start from 0434's kit examples, moved to v0.1 and extended.

Four processes are in the set: two ways to log a repair (portal `aaaa11112222`, phone `bbbb33334444`), the main step that schedules and completes it (`cccc55556666`), and a visit reminder (`eeee99990000`). Paying the repair firm (`dddd77778888`) is a context neighbour. The repair firm is an `actors[]` entry of kind `external_party`, drawn as the external lane.

| Case | Where |
|---|---|
| Recovery steps inside a sub-task | Box `b2` (and `b2f` in the future state): `recovery[]` badge `st-005`–`st-006`, which sit inside the box's own sub-task steps. |
| A write-only state drawn as a chip | `s-waiting` ("Waiting on repair firm"): one `sets_state` edge in from `b3`, no edge out, not an end. The state node and its edge stay in the data; the renderer draws it as a "Sets: …" chip. |
| Chip exception: another process reads it | `s-booked` ("Visit booked"): written by the main step, read by the reminder process (`b6`, link `lk-reminder`). Stays a pill. |
| Chip exception: a handoff passes through it | `s-logged` ("Logged"): handoff edges from both entry boxes and on to the main step. Stays a pill. |
| Chip exception: an end | `s-closed` ("Closed"): `terminal` in the set map and in `outcomes`. Stays a pill. |
| Two agents in one AI and agents lane | Future state: `ag-intake` tagged `agent: intake-agent`; `ag-pick` and `ag-book` tagged `agent: scheduling-agent`. All three sit in the one lane `ai`. |
| A replaced AI use is not drawn | Future state: the failed chat-assistant use `ai1` has no node; `ag-intake` lists it in `future.from`. |
| Every work node names its process | Sub-task boxes, decisions and the AI use carry `process_id`; the routing decision `dec-channel` uses the reserved value `set`. |

The test also proves the schema refuses, one case each: an `agent` tag on a current state, a second AI and agents lane, a work node without `process_id`, a split without `split_pair`, a recovery badge without `step_ids`, and an unknown extension id.

The examples were generated by a script kept with the building unit's run records, which are not shipped; edit them by hand and rerun the schema test.
