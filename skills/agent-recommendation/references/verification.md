# Verify outputs and evaluate the method

## Verify this recommendation run

Check the delivered report against the original discovery ledger, not only a shortened renderer input. Correct material failures before delivery; explicitly mark unresolved evidence gaps rather than certifying them.

1. **Scope:** reconcile requested process IDs, retrieved pages, actual narrative reads, source inspections and dispositions. For a complete-census claim, verify the stated coverage against the frozen inventory. Explain inaccessible and zero-observation entries.
2. **Identity and counts:** recompute available/read/source counts from saved records; separate records, work units, business events, retries and batches. Confirm no shared event or benefit was counted twice. Give definitions/denominators for friction, cadence and exception claims. Unknown event independence remains unknown.
3. **Cross-process content:** compare each candidate's exported process memberships and typed edges with its discovery record. Explain intentional splits, omissions or rejected links. Catch a many-process candidate being reduced to one source, even when the generated HTML faithfully matches a truncated intermediate file. Conversely, do not add unrelated processes to meet a quota.
4. **Grounding:** open/check the sources behind material claims. Mark captured, derived, supplied, researched and assumed statements. Distinguish observed handoffs from proposed bridges, source access from actual inspection, setup from repeated execution and reported success from measured value.
5. **Constraints and authority:** carry the supplied objective and long-text landscape/constraints through to each solution. Check allowed forms, actual access, controls a named person keeps, ownership and proposed writes. Do not call prohibited or foundation-missing scope ready.
6. **Reasoning:** require a useful recipient/output, credible competing explanation, visible ignore-if condition, simpler alternative, qualified impact and a discriminating next test. Review total effort and shared benefits, not only generation speed.
7. **Feedback stage:** check that initial hypotheses identify promising work and request corrections and targeted artifacts. “Move forward” must produce the selected evidence request unless sufficient material is already available. Before refinement, verify actual contents inspected, corrections applied, how artifacts changed current-state understanding and dependent gaps retained. Reuse valid previous answers. Selection or a UI click alone is not implementation authorization.
8. **Research:** verify original URLs/locators, actual passages read, dates, source lineage and evidence class. Check that claimed X API calls and podcast inspection happened. Reconcile external-to-local differences and state how research changed the recommendation.
9. **Report spec:** verify Objective → Current state → Recommendations; attributes, Work Brain process references and Detailed Current State; shared assumptions/ignore-if; each solution's what, proposed future state, impact/reasoning, selection summary/details and next steps. For an initial report, include both a usable continuation prompt and tailored artifact requests. For a refined report, check the Stage 2 items in step 11 instead; it has no investigate continuation prompt. Ensure the new chat can understand the scope without this conversation.
10. **Reusable output:** render from the bundled user template and current report JSON. Inspect the populated HTML itself: no inherited sample claims, complete objective/constraints, long text, disclosures, arbitrary candidate IDs, empty-state behavior, keyboard/narrow-screen use, prompts that can be selected and copied, and tailored evidence requests. Confirm the report/evidence travel together, the page carries no script and no external fetch is needed. Do not claim render/interaction checks from source inspection alone.
11. **Stage 2 verdicts (refined report):** the renderer validates the verdict fields (see [the report data model](html-data-model.md)); check these producer obligations it cannot:
    - every design-brief `process_id` is a Within resource key from the MCP, not a name or a made-up id;
    - `stage1_recommendation_id` is the id of the Stage 1 recommendation the person picked, and round 1 is saved as `report-refined-<recommendation id>.json`, `recommendations-refined-<recommendation id>.html` and `recommendations-refined-<recommendation id>.evidence.json`, so a second recommendation refined from the same run never overwrites the first; before saving, no other file in the run folder has the same name ignoring case (macOS file names ignore case, so `QUAL-A` and `qual-a` would collide), unless it is this same report's earlier copy (same recommendation id, same round and, for round 2, the same blocked solution id);
    - each brief's objective names how success is judged and the owner (a named person or role);
    - each don't pursue reason names the simpler route (an owned feature, ordinary automation, a process fix) and who would take it, when one exists;
    - each readiness basis is real: it cites the evidence that meets that condition;
    - each brief's `future_state` and `limits_and_authority` are consistent with the card's `future`, `agent_does` and `people_keep`;
    - each blocked solution names one deciding item in `blocking_item`; any needed-now request it carries is that item, and every other gap is `later` (the renderer refuses two or more needed-now requests on a blocked solution);
    - in a round-2 report, every solution descends from `round2_basis.blocked_solution_id` (other blocked solutions stay in their round-1 report), and `round2_basis.item_brought` really answers the blocking question; if it does not, the solution ends don't pursue with the reason naming what is still missing; round 2 keeps the round-1 `stage1_recommendation_id` and is saved as `report-refined-<recommendation id>-r2-<solution id>.json`, `recommendations-refined-<recommendation id>-r2-<solution id>.html` and `recommendations-refined-<recommendation id>-r2-<solution id>.evidence.json`, where the recommendation id is `stage1_recommendation_id` and the solution id is `round2_basis.blocked_solution_id`, leaving the Stage 1 and round-1 files untouched;
    - Our recommendation names the one solution most worth acting on first, says why and gives the next step.

Record what passed, what remains unknown and the limits of the check. If scores or quantitative comparisons were actually used, retain inputs/config/version and recompute them; never treat arithmetic verification as evidence that the recommendation is useful. Historical v3 checks validate only that historical engine.

## Evaluate a skill change

Use frozen, dated evidence with comparable scope, retrieval budget and available information for before/after comparisons. Preserve raw inputs and the skill/config versions. Separate a behavioral test on synthetic fixtures, a retrospective replay, a prospective held-out evaluation and a live trial.

- Split holdouts by underlying episode or work family, not duplicated observation rows. Known internal success stories help explain the theory but do not provide independent predictive validation.
- Have owners assess recognizable work and useful outputs before seeing agent designs. Mask counts/titles where the question warrants it; report what could not be blinded.
- Include negative/boundary cases: dense coordination, fixed transfers, broken integrations, setup-only records, missing standards, one-specialist work and similar language with incompatible standards. A correct result may be no new agent.
- Measure useful nominations, independently found missed opportunities, unsupported joins/claims, unnecessary builds, duplicated benefits, confidence calibration and appropriate revision after feedback. Report disagreements instead of fitting weights to favorable examples.
- Check content fidelity through discovery → candidate data → final report. Specifically test repeated projections/retries, unsupported cadence, cross-process membership loss, prohibited platforms, selection without artifacts, already-supplied artifacts, safe population of the reusable template and unavailable research routes.
- Test the observation-count proxy separately using independent event identity and coverage. Purposive contrasts do not establish a correlation coefficient or a universal threshold.
- Trial selected help separately: accepted quality, serious errors, total human effort, continued use and maintenance against current practice and a simpler alternative. Passing packaging checks or a hypothetical replay is not proof of field performance or ROI.

For a meaningful skill update, give an independent reader a realistic task, the candidate skill and only the needed raw evidence; do not supply the expected answer. Inspect the actual output and fix instruction failures. Report the number and nature of tests honestly; do not imply a full production rerun.
