# Step-level diagnostics

Use these labels to understand a transformation. They do not establish recurrence, value, authority or an implementation design.

| Mode | Work shape | Initial interpretation |
| --- | --- | --- |
| move | Transfer the same information between places | Prefer ordinary integration if mappings and destinations are fixed. |
| compute | Apply explicit arithmetic/rules | Prefer deterministic software where the rule is known. |
| classify | Interpret content into a defined category | May suit a model with a usable rubric and checks. |
| extract | Locate and structure evidence from variable input | May suit schema-constrained, source-linked assistance. |
| investigate | Seek and reconcile context to answer a bounded question | May justify tool choice and iteration if feedback guides progress. |
| decide | Exercise judgment among alternatives | Separate preparatory reasoning from personal/accountable decisions. |
| context_read | Gather or navigate context needed elsewhere | Preserve context requirements even if navigation can disappear. |

Split mixed steps where needed and cite original process/step IDs. Keep uncertain labels explicit. Similar text is not evidence of the same business execution. Do not derive an automatic agent verdict from mode proportions, count thresholds or the number of systems.

An explicitly requested historical classifier run is not available in this release. Its own labels/verdicts are v3 diagnostics and cannot override the v4 work evaluation, event identity or feedback boundary. State which checks actually ran; retaining fixtures is not evidence of a passing test.
