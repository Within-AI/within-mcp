# Test-suite stage

Read only inside this run's folder and the plugin; never list or open folders beside the run.

You write the test suite for the agent design in this run. The suite is built the way our shipped agents were tested: typed outcomes per decision, cases with concrete rows and exact expected values, cases in layers, and code checks first. Keep known numeric outcomes as JSON numbers and text as text. For computed results, name the method and its available inputs; `scripts/compute_expected.py` computes them exactly. People review the suite; agents run it later in simulation.

## Read
- `stages/intake/intake.json` (process count; `observations.snapshot_intake` for observation ids).
- `stages/architecture/agent.yaml` (JSON syntax): the parts and the header `handovers`.
- `stages/boundaries/boundaries.json`: the interfaces, the gates, and which hand-offs reach a person.
- `stages/rules/rules.json`, `stages/rules/open-items.json`.
- `stages/rules/outcomes.json`: the typed outcomes.

## Method

1. **Typed outcomes.** Read the typed outcomes from `stages/rules/outcomes.json`. Never re-type them: use each label exactly as written there, per decision and per gate. Never reduce an outcome to a bare "recommended" or "escalated". A label not in `outcomes.json` fails the check.
2. **Per-decision cases.** For every decision in `outcomes.json`, write cases with concrete rows (a row id and its column values) and exact expected values: `expected.label`; in `expected.values`, every boolean, text, `null` and not-applicable value as itself; and known numbers as JSON numbers, with optional derivations in `expected.derivations` (method 12). A case whose numbers are all derivations, with no literal value, is complete. A case with empty rows, or with neither expected values nor derivations, fails.
3. **Kinds.** Every decision has at least one case of each kind: `positive` (the agent proposes or completes), `must_escalate` (the agent must stop or hand to a person) and `boundary` (the edge of a condition).
4. **Layers.** Write cases in four layers: `part` (per part), `handover` (between parts), `end_to_end` and `authority` (what the agent must never do on its own). Declare a layer in `omitted_layers` with a reason only when the shape has none; with two or more parts the handover layer is never omitted. Each handover case records, under `interface`, the boundary id and the sub-agent's input and output at that interface.
5. **Hand-offs to people and steps a person decides.** Every hand-off that reaches a person gets one case per outcome label of its gate. Every gate a person decides (its boundary comes from a person) gets at least one case per gate label, and each such case states the person's decision as synthetic data: `"person_decision": {"gate": "<gate id>", "decision": "<one of that gate's labels>"}` (add `"ends_process": true` when that decision ends the process, and expect `"next_step": "ended"` in `expected.values`). The simulation plays that decision at the gate and grades what the agent does next against `expected`; a case with no decision cannot be walked.
6. **Gates.** One case belongs to one gate. Never pool a case across two gates.
7. **Escalation conditions.** Every escalation condition (an outcome label that hands the item to a person: any decision label that is also a label of a gate whose boundary goes to a person, and any label that says it is escalated) has a `must_escalate` case expecting it, or a stamped-open exclusion.
8. **Critical cases.** Mark a case `critical: true` when its failure fails the whole suite. A critical case may list allowed alternative outcomes in `allowed_alternatives`, each with its own expected values; only critical cases carry them.
9. **Stamped-open exclusions instead of invented answers.** When a rule is missing or an item is open, do not invent an answer. Write an exclusion: `{"id", "decision", "kind", "layer", "reason", "evidence_state", "exclusion": {"missing": "<open item id, or 'missing rule: <what>'>", "stamp": "needs_more_information"}}`. The `missing` text names the open item id from `stages/rules/open-items.json` or the missing rule. An exclusion with a `layer` counts as declared, incomplete coverage of that layer, so a layer whose every case is open is covered by its exclusions.
10. **Rows never hold what the agent decides.** Rows are inputs only. A column the case's decision sets (any key of `expected.values`) never appears in a row.
11. **Labelled values.** Every row value is `{"value", "label"}` with label `observed` or `synthetic`. An `observed` value carries `source_ref`, an observation id of the form `<prefix>observation:<resource_key>` whose resource key is in the snapshot intake. Invented values are `synthetic`, never observed.
12. **Types and calculation evidence.** Derivations are optional for known numeric outcomes. Preserve numeric values as JSON numbers; keep numeric-looking identifiers as text. Convert decimal text only when a derivation or an authored `amount_direction` declares numeric semantics. For a computed result, supply the method and its available inputs. Prefer a named derivation: `{"derive": "<name>", "inputs": {"<token>": {"read": "<row_id>.<column>"}}}` with a name from `copy`, `negate`, `absolute`, `sum`, `difference`, `absolute_difference`, `product`, `ratio`, `round`. Inputs are taken in the order written. The node form also works (`read`, `calc`, `literal`); preserve existing authored methods and their input order. Do not compute amounts in this prompt or invent absent inputs to fill a derivation. `scripts/compute_expected.py` emits computed amounts as JSON numbers and retains the authored derivations. A derivation may cite only rows the case has. Keep unknown amounts as `null` or a stamped-open exclusion with the missing information; never replace them with zero. The same rules apply to allowed alternatives. Keep evaluator answers separate from runnable inputs.
13. **Amount direction.** For every expected amount, add `expected.amount_direction`: `{"<amount name>": "credit" | "debit" | "needs_more_information"}`. Use `credit` or `debit` when the inputs state it, else `needs_more_information`; never guess a direction. A token in `stages/rules/rules.json` that declares an `amount_direction` needs one on its expected amount.
14. **Judgment answers.** In `judgment_answers`, list `{"rule_id", "item_key", "answer"}` for each judged rule the case walks. Give the answer in the type that fits the scenario: text, a number, `true` or `false`, or `null` when the case tests a missing answer. Text may be empty (`""`) or `"explanation not found"` when the case tests that nothing was found. These are all different values, and each is kept as given through conversion and the simulation.
15. **Holds.** In `holds`, list for each rule the case walks `{"rule_id", "item_key", "holds"}`: `item_key` is the id of the case's row the rule is tested on, and `holds` says whether the rule holds there. A case with no holds walks no rule. The rows carry every token the held rules read, stand-ins from `stages/placement/declarations.json` included.
16. **Simulation-only.** The suite declares `"status": "simulation-only"` and `"numeric_floors": "open"`. Never give a numeric pass floor; it stays open until pilot data exists.

## Write
Write `stages/test-suite/test-suite.json`, valid against `formats/run/suite.schema.json`, each case per `formats/run/case.schema.json`. Start from `template.json` in this folder. Write nothing else.

`check_cases` then runs on the suite; fix every defect it names.
