#### The current state ignores the direction, not the set map
The current state draws the work as it is today. Ignore every design direction item (what to change, what to keep, what to bring in scope): those belong to the transformation plan and the future state. Reading the set map is different, because the set map is structure, not direction: when the run has one, the current state reads it and draws from it, and still ignores direction items.

#### Rules for every current state
- **Automation moving the work object: system band if rules-based, AI lane if AI, never left out.** A bot, scheduled job or rule that applies, updates or changes the state of the shared work object itself is its own box. If it is rules-based, it goes in the system band (the system-of-record lane). If it is AI, it goes in the AI-and-agents lane as an `ai_use` node with `mode: agent`, `tool` naming it, and its flow edge into the state it writes. Never drop it, never fold it into a state pill, never reduce it to something a person consults, and never credit its work to people's boxes.
- **The AI-and-agents lane is always drawn.** If no AI use is found in the evidence, keep the lane, set `none_found: true` on it and label it "none found". An empty lane that says nothing is not allowed.
- **Workspace short labels are chosen, never cut.** A workspace's `short_label` is a chosen short name, never a cut-off: a name you pick (for example "Outlook" for the mail client), never the full name cut off at a character count. If you have no good short name, leave `short_label` out; the renderer then draws `name`.
- **Read every observation for AI.** Read each process's observations, not only its steps, for AI or LLM outputs (a drafted email, an AI summary, a chat assistant's answer). Each one found is an AI use in the AI-and-agents lane.

#### Shape A3 for a set of processes
When the snapshot holds 2 or more processes, the Current state Workflow follows the A3 lane standard and is written in format v0.1 (the current state graph): Fast Mode's workflow bundle plus the A3 fields. Everything above still applies (`coverage`, `systems_coverage`, the checks); the renderer is the A3 one, `render_a3.py`, never the bands renderer. A fictional worked example ships with the skill's reference material; copy its shape, never its content. Write **no layout positions** (`col`, `row`, `x`, `y`, `via`, `labat`, `labfrac`) anywhere: the A3 renderer lays out the page from your data.

**The idea.** Organise the set around the shared work object(s) the processes create, hand over or wait on, and the states each object passes through, not around the processes placed side by side. Each process is a frame laid over the lanes. Links between processes are typed and carry their evidence.

**The set map.** For 2 or more processes the set-map stage runs first, and run control places the set map at `RUN_ROOT/inputs/set-map.json`. It is the structured description of how the set fits together (processes and their roles, work objects, object states and who moves the object into each, typed links with evidence, context neighbours outside the set, open points). Read the set map and draw from it; check it against the snapshot; where the snapshot disagrees, stamp Contradictory and raise an issue; never rewrite it. This stage never writes its own set map: if `inputs/set-map.json` is missing, stop and say so in your log. Point the bundle's `set_map` at `inputs/set-map.json`, written relative as shown, never as an absolute path.

**Link kinds** (set map `links[].kind`): `handoff` (one process's output object, in a state, becomes the next one's input), `variant_entry` (several processes produce the same object in the same state from different triggers), `parent_child` (a process creates an object that belongs to another, and the parent waits), `lifecycle_continuation` (a later process takes the object over in a later state, often after a wait on an outside party), `decision_gate` (an upstream check decides whether the set runs at all, or which variant), `re_entry` (a later state starts an earlier process again), `overlap` (two processes do the same work on the same object), plus `analogous_work`, `shared_knowledge`, `shared_team_or_system` (never flow; a shared team or system alone never proves any flow link).

**Evidence strength for a link, strongest first:** `shared_instances` (the same object identifiers appear in both processes' observations: one shared instance is weak, three or more is strong; a link at this level is never Assumed), `step_state` (a step writes a state the other process's trigger reads), `trigger_end_text`, `same_capture_session`, `dependency_field` (treat as undirected and check its direction against the flow before using it), `hierarchy_scope` (good for finding neighbours, not for proving flow), `shared_team_or_system`. Record the strongest level you found and where.

**Lanes (`graph.lanes[]`), in four bands in fixed order:**
1. **people**: one lane per role group that does work or makes a decision, never one per process. Requesters and recipients share the top lane. Coarse `lane`: `Analyst`.
2. **ai_and_agents**: exactly one lane, always present, coarse `lane`: `Agent`. Every current AI use found in the evidence is its own `ai_use` node here (general assistants, chat or copilot tools, AI search tools included), with `tool`, `mode` (`assistant`: a person asks and a person acts; `agent`: it acts or writes by itself), `checked_by`, `failed` (with `failure` when an AI output failed or a person had to correct it) and `evidence_strength` (`step`, `exception_note`, `observation_only`; mark the edge `weak` when weaker than a step). Link it to the person's box with one `asks_returns` edge. Ordinary automation that is not AI (rules, scheduled jobs) goes in the system band. An AI bot or automation that moves the work object goes here as its own `ai_use` node with `mode: agent` (see "Automation moving the work object" above). If no AI use is found, set `none_found: true` on the lane.
3. **system_of_record**: one lane per system that holds a shared work object's state (usually one). Coarse `lane`: `System`. It holds `object_state` pills (one per state drawn, `object_state.state` = the set map state id), rules the system enforces, and rules-based automation that moves or writes the work object, as a box.
4. **external**: one lane per outside party whose system or decision the flow waits on (group a party's systems into one lane). Coarse `lane`: `External`. Their decisions and the states on their side.

Every node has `lane_id` (its A3 lane) and the coarse `lane` of that band.

**Boxes.** One box per Work Brain sub-task on the main path (`read_interaction`, or `write_interaction` if it writes), with `process_id` and `subtask{process_id, step_range, step_ids}`. A sub-task with a business decision in the middle is drawn as numbered parts: part 1 before the diamond, part 2 after it, each part a box carrying `subtask.part{index, of}` (for example `{"index": 1, "of": 2}`); every step stays on exactly one part. A sub-task whose steps only recover from a failure (a retry, a rebuild after rejection) is not a box: it is a `recovery` badge on the box it recovers. The same applies to recovery steps inside a sub-task: they become badges on that box, not part of its main line. A conditional step is a `decision` diamond (with its decision table) only if it is a business decision (who, what, whether); a system validation is a badge. An exception that ends the work unresolved is an `end_event` with `stop{unresolved: true, reason}`, listed in `open_ends`.

**Read the exception tables.** Read every exception or issue table in each process's details (exception handling, issues, edge cases), not only the steps, and place each exception on the spine: as a `decision` where it branches the work, as a step or recovery badge where it is handled, and as a stop (`end_event` with `stop`, in `open_ends`) where it leaves the work open or waiting. Cite the table row as evidence. An exception the steps do not show is still drawn.

**Worked case: recovery steps inside a sub-task (fictional).** Northwind's "Check supplier invoice" sub-task runs steps 4–9. Steps 4, 5 and 9 are the main line (open the invoice, match it to the order, mark it matched). Steps 6–8 only happen when the match fails: ask Acme Parts for a corrected invoice, wait, re-open it. Draw one box for steps 4–9 with a `recovery` badge for steps 6–8 listed in the box's tooltip; do not draw steps 6–8 as their own box or on the main line. If the failed match can also end with the invoice rejected and nobody following up, that outcome is a stop in `open_ends`.

**Decisions sit in the lane of whoever decides**: a person's in their lane, an outside party's in the external lane, a system rule in the system lane. Read every roles or responsibilities table in each process's details and name the decider for each decision from it (who approves, who signs off, who owns the call), citing the table row. Mark "who decides" as needs more information only when neither the steps nor any roles table names one. Sign-off from a role outside the box's lane is a `person_check{role, what}` on the box, with no edge to a lane that has no work of its own.

**Systems appear only three ways:** as states of the shared work object (pills, with handoff edges in and out); as a `writes[]` line on the box for other records written (draw an edge only when that record is a second shared object later work reads); as tool lines through the box's `systems` (pointing at `workspaces[]`). AI tools never appear only as a tool line. No system rails. Every inventory system still gets a `systems_coverage` row; a system on no box is cut with the reason.

**Frames and objects.** `graph.process_frames[]`: one per in-set process (`process_id`, `name`, `role`, `key_control`). `graph.work_objects[]`: each object drawn, with its set map id.

**Flow between processes.** Every handoff between processes passes through a work-object state pill (`handoff` edge into the pill from the producer, flow out to the consumer), or is a direct `handoff` edge with its evidence. Variant entries share one start and a decision that chooses between them; if the routing rule is not recorded, the decision says so (needs more information) with an open issue, never an invented rule. A step that writes a state without handing over uses a `sets_state` edge. A re-entry is a `loop` edge. Edges that draw a set map link carry `link_ref`.

**Work outside the set.** Each context neighbour that touches the spine is one `context_neighbour` node (`neighbour{process_id, touches}`) in its performer's lane (or the requester's lane if its performer has none), attached where it touches; every edge to or from it has `context: true`. When a process can stop at a waiting state, name what resolves the wait, even when it is outside the set.

**Before you finish**, run the A3 checks this stage carries for a set of processes (the format check on the graph and the A3 current-state check, with the set map and the snapshot) and fix what fails where the evidence allows. A check you cannot pass without inventing facts stays failing; say why in your log. If the current state graph format cannot express something this standard needs, do not invent a field: write it under "Plugin problems observed" as a format gap.
