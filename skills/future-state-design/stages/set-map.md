### set-map — Set map
- Runs: only when the snapshot holds 2+ processes and the design direction carries no set map that covers every snapshot process (a map scoped to the recommendation's processes does not stand in for it). This is the separate set-map step that comes before the drawing stages: a set map is a required input to Future State Design for two or more processes, and when none is given, this stage writes one first.
- Reads: `inputs/snapshot.json`, `inputs/snapshot-intake.json`, the `get_process_*.json` files in `inputs/`, and `inputs/set-note.md` when present. Facts come from the snapshot and the set note alone.
- Shape: set map **v0.1** (`"set_map_version": "0.1"`). Copy the shape of the set-map example in `KNOWLEDGE_ROOT/checks/formats/examples/` and validate against the set-map v0.1 schema beside it in `KNOWLEDGE_ROOT/checks/formats/`; the example is fictional, so copy its shape, never its content. No worked reference is registered for this stage, so there is no reference block, no `reference_use` record and no copy guard.
- Produce in `stages/set-map/`: `set-map.json`, and nothing else. Do not write `inputs/set-map.json`: run control copies your file there, with its hash, when this stage's checks pass.
- Checks: `checks/check-a3-format.py --run RUN_ROOT --stage set-map --kind set-map`, `checks/check-evidence-freeze.py --run RUN_ROOT --stage set-map` and the skill's own `scripts/check_set_map_movers.py --run RUN_ROOT --stage set-map`.

**What a set map holds.** The structured description of how the processes in the set fit together, which the later stages draw from:
- `processes[]`: each in-set process with its role (`entry_variant`, `main_step`, `closing_step`, `upkeep`, `gate`, `other`), trigger, end, and the states it reads and writes.
- `work_objects[]`: the shared work objects the processes create, hand over or wait on (system of record, identifier pattern, relations).
- `object_states[]`: each object's states in order, with `moved_in_by` naming the process, context neighbour or actor that moves the object into each state.
  An object state moved in by two or more actors needs an overlap link, a variant entry or an open point about it, at this stage: an `overlap` or `variant_entry` link whose `state` is that state, or an entry in `open_points[]` whose `about` names it. The set-map check fails such a state here, before the current-state stage draws it.
- `actors[]`: the one list of performers that move a state or write an object but are not processes, each with `id`, `name`, `kind` (`external_party`, `rules_automation`, `ai_automation`, or `other` with `kind_text`), optional `system` and `writes_objects`, and `evidence`. A bot or rules engine that applies or updates the shared object itself is an actor here, never credited to people.
- `links[]`: typed links between processes, each with its evidence (below).
- `context_neighbours[]`: work outside the set that touches it, attached to the state or process it touches.
- `open_points[]`: what the evidence does not settle.
- `snapshot_cutoff`: the snapshot's cutoff (`inputs/snapshot.json` `scope.cutoff_at`), copied exactly. `process_versions[]`: one `{process_id, version_no, created_at}` entry (plus `version_key` when known) for each process version the map was built from, taken from the snapshot, so drift against the freeze can be seen. Keep `evidence_cutoff` as free text beside them. If the snapshot carries no cutoff or no version for a process, do not guess one: say so in an open point and in your log.

**Link kinds** (`links[].kind`): `handoff` (one process's output object, in a state, becomes the next one's input), `variant_entry` (several processes produce the same object in the same state from different triggers), `parent_child` (a process creates an object that belongs to another, and the parent waits), `lifecycle_continuation` (a later process takes the object over in a later state, often after a wait on an outside party), `decision_gate` (an upstream check decides whether the set runs at all, or which variant), `re_entry` (a later state starts an earlier process again), `overlap` (two processes do the same work on the same object; never a flow link and never resolved silently), plus `analogous_work`, `shared_knowledge`, `shared_team_or_system` (never flow; a shared team or system alone never proves any flow link). Set `flow: true` only on the six flow kinds. If a variant's routing rule is not recorded, `routing_rule` stays null with an open point, never an invented rule.

**Find recurring identifiers first.** For every pair of processes, search the observations and the step text for object instance identifiers (case numbers, request ids, record keys) that recur across processes, before you settle any link's evidence level. Count the distinct shared identifiers per link in `shared_instance_count` and record where you found them in `evidence_refs`. A link with shared identifiers that you leave at a weaker level, or stamp Assumed, is a defect.

**Evidence strength for a link, strongest first:** `shared_instances` (the same object identifiers appear in both processes' observations: one shared instance is weak, three or more is strong; a link at this level is never Assumed), `step_state` (a step writes a state the other process's trigger reads), `trigger_end_text`, `same_capture_session`, `dependency_field` (treat as undirected and check its direction against the flow before using it; record that check in `direction_evidence_state`), `hierarchy_scope` (good for finding neighbours, not for proving flow), `shared_team_or_system`. Record the strongest level you found and where.

**Evidence states and refs.** Every link (and every other entry whose shape in the example has an evidence state) carries one of `Observed`, `Assumed`, `Contradictory`, `needs_more_information`. Anything not in the snapshot or the set note is an open point (`needs_more_information`), never a guess. Who decides what comes from the processes' roles and decision tables where they say so. Every evidence ref resolves to the snapshot index (`sources[].id`, `issues[].id`, `required_source_ids[]`); content captured after `snapshot_cutoff` is not Observed.

**How the later stages use it.** The current-state stage reads only `inputs/set-map.json`, draws from it, and must check it against the snapshot; where the snapshot disagrees, stamp Contradictory and raise an issue; do not rewrite it. So write the map once, from the evidence, and put every doubt in `open_points[]` rather than smoothing it over.

**Before you finish**, run both checks above and fix what fails where the evidence allows. A check you cannot pass without inventing facts stays failing; say why in your log. If set map v0.1 cannot express something this stage needs, do not invent a field: write it under "Plugin problems observed" as a format gap.
