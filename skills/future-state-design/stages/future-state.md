  - **2 or more processes (A3):** `python3 KNOWLEDGE_ROOT/renderer/render_a3.py future-state.input.json . --stem future-state`.
  - **One process (bands):** `python3 KNOWLEDGE_ROOT/renderer/render_workflow.py future-state.input.json future-state.json future-state.svg`.
- Produce `stages/future-state/future-state.input.json` and the rendered bundle, SVG and HTML. Every snapshot system either stays on a future-state node or is cut with a reason.
- Write stance. Unless the evidence says otherwise: (1) the agent reads any system named in the evidence; read access is Assumed. (2) Agents write by default: notices and reports to the person, drafts, handoffs to agents and people, their own files, `mechanical` writes (values nobody chose: confirmed by a person, or copied unchanged from a named source) and `decision-bearing` writes into a system of record (a value, submission or status change the agent chose). The agent may make decision-bearing record writes. (3) A person keeps a step only for one of the three reasons in the transformation map's Why people stay section (`control`, `outside party`, `client statement`); every other step is the agents' work. (4) Confirm-then-enter is optional, not mandatory: keep a person's confirmation before a write only where the evidence calls for it, and otherwise let the agent decide and write. (5) The exception reasons `own-working-surface` and `reversible-reviewed` stay valid values but are descriptive only; an agent needs none to write. Each one used is stamped Assumed and listed in What we still need to know. (6) System of record means the authoritative store; if it is unclear whether a system is one, treat it as one. (7) Write access and route (API, MCP, or screens and a browser) are always Assumed, never confirmed by the design; list each under What we still need to know. (8) The agent may make decisions, including routing, dispatching, escalating and the decisions behind its own writes; on a `control` step the decision itself is the person's, and the agent feeds it a recommendation. (9) Every step the agent takes states what it reads or writes, the write grant id, and the kind of access, never a sequence of screen clicks. A request for a report from an Oracle system is a data pull through an API read, not a restated click sequence; if a read needs a report job to run first, state that as an access assumption and mark it needs more information. (10) The references show agents that write nothing; the write stance governs where they differ, and you record the departure in your REFERENCE-USE divergences. Where the evidence is unclear about a write, take the best-supported reading, say why in one line and continue. Before you finish, check two things: every step the agent takes states what it reads or writes, its write grant id and its kind of access; every judgment unit is named. People can change these assumptions after they see the result.
- **Ambition audit (optional input, the rework round).** When `stages/pass-1/ambition-audit/ambition-audit.md` exists, read it alongside the reworked map: draw the future state the reworked map describes, using the audit to see what the rework changed. The map's stage writes the response to each proposal; this stage writes no response file. Where the audit and the reworked map differ, the map wins; say so in one line and continue. When the file does not exist, skip this.
- **Redraw from the reshaped steps, don't copy and relabel.** Draw the future state from the map's reshape moves and assign pass; do not copy the current-state graph and change lanes. Every adopted move's Future steps exist as nodes. Steps a move removes are gone; a merge may keep at most one of its current step ids, and only as the merged step (one of the move's Future steps), and the rest are gone. For both, their coverage rows are `summary` citing the move ("removed by RM-n" or "merged into RM-n"). Every current ending in the map's Outcomes table maps to a future end event reachable from a start, or is `retired`.
- **Every path keeps the person's confirmation.** Before you finish, walk every path from each start to each end, including reset, recovery, retry, exception and escalation branches. (a) Where the map keeps a confirmation step for a write, no path may reach the agent step that makes that write without first passing the person's confirmation of those values; a write the map gives the agent with no confirmation step needs none. A reset or recovery branch that loops back to an agent write goes back to that confirmation (or before it), unless it only re-enters values already confirmed with no new value chosen; say that on the edge label. (b) An exception, escalation or handoff edge may not jump past a person's kept decision, approval, submission or confirmation and rejoin the flow after it. Route it back to that step (or before it), or branch from a decision node whose condition says why the step does not apply on that path. (c) A conditional branch of today's graph (for example, a step taken only when some support is needed) keeps its condition on every future route that can reach it.
- **One AI and agents lane in every future state, always.** This holds for multi-process A3 runs and single-process runs alike. Draw exactly one lane for the AI and agents band, with the coarse `lane` value `Agent`: one per run, never one per process or one per agent. Never draw an `Agent: <name>` lane and never a second AI lane. Agents are told apart by an `agent` tag: every node in the agent lane carries the node key `agent` with the name of the agent the map gives it (with one agent, every agent node carries that one name). Every agent step carries its tag, one agent or many: a designed-agent step with no `agent` tag, or a blank one, fails the lanes check; only an `ai_use` in assistant mode (a tool a person uses) goes without. The map's named sub-agents share the one `Agent` lane and differ only by tag: one AI and agents lane with `agent` tags, never one per named agent. A kept or upgraded current AI use sits in the same lane. The `agent` tag is for future states only; a current state never carries it.
- **Every agent node that writes names its write grant.** It carries `write_grant: "WG-<n>"` (from the transformation map's Write grants table) as a data field on the node; a step that carries more than one grant lists them all, `write_grant: ["WG-2", "WG-4"]` (a hand-off on an exception path is a grant too). Use the one field; do not add a second `write_grants` list that says something else. Never write the grant id, or any other internal id (`RM-n`, `WG-n`, `DD-n`, source, issue or node ids), into a displayed `label`, `display_label` or `notes`; the step's read, write and access kind stay in plain words there.
- **Always draw what the agent writes to.** Every system in the map's Write grants table sits on a future node's `systems`, so each grant's target shows in the diagram.
- **Every node records where it came from.** In a single-process run as in a set, every node carries `future.from`: the current-state node ids it comes from, or `[]` for a new step. A Write grants row's Steps name current-state ids, and they resolve to future steps only through `future.from`.
- **The Write grants table is an input; judge it, never edit it.** Draw each grant on the steps the evidence supports. Where a row disagrees with the map's own text or the flow you draw (for example its Steps name steps that come before the person's confirmation, while the map says entry follows confirmation on every path), draw what the evidence supports and record the reading you took in a `grant_readings` list at the root of `future-state.input.json`: one object per grant and column, `{"grant", "column", "table_says", "read_as", "rules", "reason"}` (the writes-and-scope check below gives the fields). A recorded reading with a reason is flagged, not failed, and the future-state page shows it beside the table's value; a reading with no reason does not count.
- **No experiment caveats as client statements.** Notes about how this skill was tested, or what an earlier experiment found, never appear in a node, an edge, a note or a client-facing summary as if they were facts about the client's work.
- **Every open item from the map is kept or recorded as closed, never dropped.** Each `- <id>: <reason>` open item in the map's What We Still Need to Know section is either kept (the same id in `graph.issues`) or recorded in the top-level `opens_closed` list of `future-state.input.json` as `{"id", "resolution", "by", "reason"}`, with a non-empty reason. An item kept under a new id is `same_as`: `by` is the new `graph.issues` id, and the old id leaves `graph.issues`. An item the evidence shows false is `found_false`: `by` names the evidence ids or file, and the id leaves `graph.issues`. `scripts/check_open_ids.py` fails an open item that is neither kept nor recorded (`open-dropped`).
- **When the current state follows the lane standard** (its bundle's `extensions` lists `a3-lanes-v0.1`, the shipping format, or `a3-lanes-v0` in an older bundle being read; skip this block only when it lists neither). The future state follows it too:
  - Keep `extensions`, `set_map`, `graph.lanes`, `graph.process_frames` and `graph.work_objects` from the current state; add the one AI and agents lane from the map's `## Lanes` in the AI and agents band (or a new system lane marked as new access). Every node carries `lane_id` and `process_id`. Keep the coarse `lane` field (`Analyst` for people's lanes, `Agent` for the agent lane and for current AI uses, `System`, `External`).
  - Every node also carries `future`: `{"from": [current node ids, or [] for a new step], "change": kept | assigned | split | merged | new | upgraded, "moves": [RM ids], "split_pair": [the other parts' ids, on every part of a split], "spans": [other process ids, for a cross-process step]}`. There is no `replaced-by` value.
  - Frames are kept, and cross-process steps list the frames they span (`future.spans`). Every work node, including a new agent step, sits in a current frame.
  - `object_state` and `context_neighbour` nodes are carried with their ids and fields unchanged, and the edges into and out of them follow the reshaped flow. Re-entry loops and context edges are kept. Context stays context unless the direction brings it in scope. A context neighbour becomes a frame only when the design direction brings it in scope, and then its steps come from the snapshot.
  - Current AI uses: a kept or upgraded use stays an `ai_use` node with the same id (an upgrade updates `mode` and `checked_by` and says what changed in `detail`). A replaced use is not drawn. The agent step that takes its work lists the use's id in `future.from` with `change: assigned`, and the map's `## Current AI uses` row names that step. Person-to-AI edges stay `asks_returns`.
  - Splits take one column: the parts of a split sit at the current box's place, one above the other, and each part lists the other parts' ids in `split_pair`; `split_pair` is a list. One agent step may serve several people's boxes; it is then the agent part of each, matching the map's `## Splits` rows. A split never adds a step in sequence that today's box did not have, apart from the person's confirmation.
  - A grouped tool stays one box unless the handling differs by member; split it by member only when the evidence shows that. Unknown per-member access goes to What we still need to know.
  - `## Set links`: every flow link of the set map is carried into the future state, as the map's `## Set links` table records it.
  - Future agent steps are platform-neutral. Never name the platform the agent runs on in any node, edge or note, and never set a `platform` or `runtime` key on an agent node.
