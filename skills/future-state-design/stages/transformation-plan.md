- Write stance. Unless the evidence says otherwise: (1) the agent reads any system named in the evidence; read access is Assumed. (2) Agents write by default: notices and reports to the person, drafts, handoffs to agents and people, their own files, `mechanical` writes (values nobody chose: confirmed by a person, or copied unchanged from a named source) and `decision-bearing` writes into a system of record (a value, submission or status change the agent chose). The agent may make decision-bearing record writes. (3) A person keeps a step only for one of the three reasons in the transformation map's Why people stay section (`control`, `outside party`, `client statement`); every other step is the agents' work. (4) Confirm-then-enter is optional, not mandatory: keep a person's confirmation before a write only where the evidence calls for it, and otherwise let the agent decide and write. (5) The exception reasons `own-working-surface` and `reversible-reviewed` stay valid values but are descriptive only; an agent needs none to write. Each one used is stamped Assumed and listed in What we still need to know. (6) System of record means the authoritative store; if it is unclear whether a system is one, treat it as one. (7) Write access and route (API, MCP, or screens and a browser) are always Assumed, never confirmed by the design; list each under What we still need to know. (8) The agent may make decisions, including routing, dispatching, escalating and the decisions behind its own writes; on a `control` step the decision itself is the person's, and the agent feeds it a recommendation. (9) Every step the agent takes states what it reads or writes, the write grant id, and the kind of access, never a sequence of screen clicks. A request for a report from an Oracle system is a data pull through an API read, not a restated click sequence; if a read needs a report job to run first, state that as an access assumption and mark it needs more information. (10) The references show agents that write nothing; the write stance governs where they differ, and you record the departure in your REFERENCE-USE divergences. Where the evidence is unclear about a write, take the best-supported reading, say why in one line and continue. Before you finish, check two things: every step the agent takes states what it reads or writes, its write grant id and its kind of access; every judgment unit is named. - **Reshape first, then assign: two passes in this stage.** Do not start from today's steps and only change who does them.
  - **Reshape pass.** Propose the future shape of the work as named reshape moves, before deciding who does any step. The eight move kinds, spelled exactly: `route at entry` (classify the work once at the start and send it down the right path), `consolidate repeated reads` (when the same data is read again before anything has changed it, read it once and reuse it; a read that comes after a write, a record being created or new input arriving is a check, not a repeat, and stays where it is), `package handoffs` (at a handoff, pass the work with its evidence, missing inputs, owner and next action; draw it as a step), `improve decision quality` (keep a person's decision but feed it a recommendation, the evidence laid out and contradictions flagged; draw it as an agent step feeding the decision), `consolidate exceptions` (gather exception paths that already exist in the current state into one place; never create a new route or path), `remove` (drop any current step the evidence shows adds nothing to the outcome; never a `control` step), `merge` (two or more steps that do the same thing on the same inputs become one; every action and check of each merged step stays in the merged step), `reorder` (change the order of steps, for example move a check before entry; say why no data dependency breaks). Add a section `## Reshape moves` before `## 1. Per-node disposition table`, with this table header exactly:
    `| Move | Kind | Current steps | Future steps | Evidence | State | How the outcome is kept |`
    Move: `RM-<n>`. Kind: one of the eight kinds above. Current steps: the current-state node ids the move touches. Future steps: the ids of the future-state nodes the move produces or keeps (the ids the Future state Workflow will use). Evidence: ids from `inputs/snapshot.json` (`sources[].id`, `issues[].id`) or current-state issue ids that show the problem the move fixes. State: `Assumed`, or `not adopted: <reason>` for a move the future state does not carry. How the outcome is kept: the current ending(s) the move still reaches and how. Use only the client's evidence; never invent volumes, rules or flow. One move per instance of a kind.

(ii) Reorder: move an existing step; never create a new check or validation whose rules are not in the evidence. (iii) Evidence: cite the snapshot source ids (for example `process-details-steps-2-4`) or issue ids behind a step, never a current-state step id on its own; a step id is not evidence.
  - **Cross-process moves only for a set.** A move whose Current steps span several processes is allowed only when the run has several processes; in a single-process run every move stays inside the one process.
